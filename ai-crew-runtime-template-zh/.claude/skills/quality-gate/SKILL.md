# 质量关卡 — 决策框架

## 目的

提供可重复、可证伪的质量审查方法，任何审查员或对抗性审查员 agent 均可应用于任何交付物。框架产出的发现带有显式严重度（HARD/SOFT），每条可追溯到具体标准。

## 何时使用

- 审查员：在签署交付物为提升就绪之前
- 对抗性审查员：在结束红队 pass 之前
- 执行者：在交接前的自我审查中

## 何时不使用

- 当交付物处于早期草稿阶段，执行者明确请求「粗略反馈，非正式审查」
- 当项目尚未声明质量标准——先定义标准

## 五个审查维度

对每个维度，审查员检查交付物的每个承重元素：

### 1. 证据 / 来源支撑

- 每个承重断言是否引用了来源？
- 来源等级（A/B/C/D）是否与断言的权重匹配？
- 如果断言是 C 级，不确定性在交付物中是否可见？
- **HARD 如果：** 承重断言无来源，或来源与断言矛盾。

### 2. 过度断言 / 过度声明

- 是否有动词在无引用的情况下断言知情、意图、因果关系或罪责？
- 结构性放置（句序、段落相邻、视点聚焦）是否暗示了来源不支撑的内容？
- **HARD 如果：** 承重断言高估了其证据等级。**SOFT 如果：** 非承重句子可以更严谨。

### 3. 反方论证存在

- 每个主要断言是否承认其最强反方论证？
- 反方论证在被回应前是否被公平陈述（钢化）？
- **HARD 如果：** 主要断言无反方论证而一个明显存在。**SOFT 如果：** 反方论证存在但可更强。

### 4. Schema / 结构合规

- 交付物是否包含所有必需的 schema 字段？
- `Handoff:` 字段是否填写了指定的下一个负责人？
- 证据等级、假设和开放问题是否声明？
- **HARD 如果：** 必需 schema 字段缺失或交接未署名。

### 5. 内部一致性

- 交付物是否自相矛盾？
- 是否与同项目其他交付物矛盾？
- 分类标签或分类体系是否使用一致？
- **HARD 如果：** 矛盾影响承重断言。**SOFT 如果：** 非承重框架存在微小不一致。

## 严重度分类

```text
HARD = 断言未被引用来源支撑
     | 必要引用缺失
     | 质量标准违反
     | 核心价值观倒退
     | 承重断言上的过度声明面
     | 承重断言上的内部矛盾

SOFT = 风格问题
     | 非承重断言可更严谨
     | 引用格式不一致
     | 反方论证存在但可更强
     | 非承重框架存在微小不一致
```

## 决策树

```
对每个承重元素：
  1. 断言是什么？
  2. 引用的来源是什么？（如无 → HARD）
  3. 来源的证据等级是什么（A/B/C/D）？
  4. 断言的确定性是否与证据等级匹配？（如过度断言 → HARD）
  5. 最强反方论证是否被命名？（如缺失 → HARD 或 SOFT 取决于断言权重）
  6. Schema 是否完整？（如缺失必需字段 → HARD）
  7. 元素是否内部一致？（如矛盾 → HARD 或 SOFT 取决于权重）

输出：每条发现的严重度。
```

## 提升建议

```text
go        = 零 HARD 发现
no-go     = 一个或多个 HARD 发现
conditional = 零 HARD，但 SOFT 发现应在下一周期解决
```

## 升级

如审查员和执行者对 HARD 发现存在分歧，升级至编排者。编排者决定或升级至项目负责人。任何 agent 不得静默推翻另一 agent 的 HARD 发现。

## 边界案例

- **交付物引用了项目来源账本之外的外部来源：** SOFT — 标记待纳入；不阻止提升，除非断言是承重的且来源不可验证。
- **执行者自我审查并声称零发现：** 审查员必须独立验证至少抽样的断言。自我审查是关卡，不是独立审查的替代品。
- **对抗性审查员和审查员对严重度存在分歧：** 编排者整合。如分歧在 HARD 发现上，更严格的分类胜出。
