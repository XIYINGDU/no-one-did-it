❯ 这是一个什么项目？

⏺ 这是一个严肃商业非虚构类图书项目，书名暂定为 《No One Did It: Responsibility 
  Laundering, from the Scapegoat to the 
  Algorithm》（《无人为之：责任洗钱——从替罪羊到算法》）。

  核心论点

  文明从未停止寻找替罪羊，只是更换了祭坛。"责任洗钱"（Responsibility 
  Laundering） 是一种反复出现的制度性手法：权力通过将责任转移给更弱的承担者、程
  序外壳、代理人、机器、市场、委员会、法律实体或记录，来维持控制或利益，同时转移
  指责、法律责任或公众怀疑。

  书的诊断框架

  对每个案例，书会追问：
  1. 谁被公开指责？
  2. 谁拥有控制权？
  3. 谁从中获益？
  4. 谁知道或应该知道？
  5. 谁本可以防止再次发生？
  6. 谁控制着记录？
  7. 谁承担了成本？

  案例分类（四种替罪羊）

  - 纯替罪羊：基本无辜的个体被指责以结案
  - 部分替罪羊：有牵连但追责停在链条底端，保护了更上层的设计者/指挥官/受益者
  - 系统/物证托辞：机器、算法、公司、委员会、程序成为被指称的"原因"
  - 成本承担羊：受害人或工人未被告罪，但承受伤害而无人担责

  当前状态

  书籍已完成 13/13 章，均处于 status: ready。当前阶段已从写作转向出版准备：提案
  包、法律审查、终稿编译和主创作者终读。

  项目使用了一个由 13 个 AI 代理组成的创作团队（架构师、叙事主笔、研究主管、事实
  核查、法律顾问、市场策略师等）来协作完成研究、写作和审核工作。

⏺ ---
  从《No One Did It》项目学习 Agent 体系设计

  这个项目是目前我见过最成熟的 Claude Code 多智能体协作案例。它不是简单地"让 AI
  帮忙写作"，而是把一本书的完整生产流程——研究、架构、写作、事实核查、法律审查、
  红队攻击、读者测试、市场策略——拆成了14 个独立 agent + 29 个技能 + 10 个 slash 
  命令 + 9 个自动化 hook，彼此通过明确的职责边界和交接协议协作。

  下面我按层次拆解，每一层都值得学。

  ---
  第一层：13+1 Agent 的角色设计

  Agent 定义在 .claude/agents/*.md，每个 agent 都是一个独立的 YAML frontmatter +
  Markdown 系统提示词。

  核心设计模式

  每个 agent 文件都遵循同一个模板：

  ---
  name: jerry-crew-chief
  description: Use when coordinating...    # 触发条件（给调用方看的）
  tools: Agent(...), Read, Write, Edit...  # 工具白名单
  model: opus                              # 强制模型
  memory: project                          # 记忆范围
  maxTurns: 40                             # 最大轮次限制
  skills:                                  # 加载的技能
    - case-file-method
    - evidence-grading
  color: purple
  ---
  # 角色定义正文
  ## Role definition — Owns / Does not own
  ## Output types
  ## Operating rules (5 条操作规则)
  ## Default response schema (强制输出格式)
  ## Hook policy
  ## Example invocations

  值得学习的设计决策：

  1. tools 字段是白名单——不是所有 agent 都能做任何事。例如 the-reader 只有 Read,
  Grep, Glob, Write，没有 Bash、没有 Agent
  调用权、没有网络搜索。laura-red-team-editor 有 WebSearch + 
  WebFetch（搜对手案例用），但没有 Agent 调用权。所有 agent 都没有 Bash 和
  TodoWrite——这两个始终在主会话层。
  2. maxTurns 按职责深度分档：
    - Jerry（总调度）：40 turns
    - 核心 lead（Bonnie/Wayne/Stephen/Laura）：25 turns
    - 法律/市场（Nancy/Blair）：20 turns
    - 研究员（Shirley/Selina/Warren/Loki）：18 turns
  3. Owns / Does not own 是每个 agent 
  的第一段正文——明确"这是我的地盘"和"这不归我管"，防止越界。

  ---
  第二层：有界调度 DAG（深度 ≤ 2）

  这是整个架构中最核心的设计——scripts/check_agent_graph.py 用代码强制约束：

  Jerry (根节点, depth=0)
   ├── Bonnie (depth=1, 叶子)
   ├── Wayne  (depth=1, 叶子)
   ├── Delon  (depth=1)
   │    ├── Shirley (depth=2, 叶子)
   │    ├── Selina  (depth=2, 叶子)
   │    ├── Warren  (depth=2, 叶子)
   │    └── Loki    (depth=2, 叶子)
   ├── Stephen (depth=1)
   │    └── Alan (depth=2, 叶子)
   ├── Laura  (depth=1, 叶子)
   ├── Nancy  (depth=1, 叶子)
   └── Blair  (depth=1, 叶子)

  关键约束：
  - 无环（静态检查拒绝任何循环依赖）
  - 最大深度 2 层（防止调度链失控）
  - 不允许反向边（子节点不能调父节点）
  - 叶子 agent 不能生成子 agent——工作产物通过 Handoff: 字段交接

  # check_agent_graph.py 的核心逻辑
  # 1. 解析所有 agent 的 frontmatter 中的 tools: Agent(...) 声明
  # 2. 构建有向图
  # 3. 检测循环（DFS）
  # 4. 检测深度（BFS 从根节点起）
  # 5. 检测反向边（子节点 depth > 父节点 depth）
  # 6. 检测不可达叶子

  ---
  第三层：异步 Handoff 协议

  Agent 不通过嵌套调用来传递工作——它们通过标准化的输出 schema 来交接：

  Owner: <agent-name> / <agent-title>
  Task:
  Inputs reviewed:
  Output:
  Evidence grade:
  Assumptions:            ← 强制非空，由 validator 检查
  Open questions:
  Risks:
  Handoff: <next-agent>  ← 命名下一个负责的人

  这非常像事件溯源（event sourcing）：每个 agent
  的输出是一份不可变的审计记录，Handoff: 字段决定了工作流的下一个节点。

  设计的精妙之处：
  - 异步解耦：上一个 agent 输出写完后，Jerry（或人类）决定什么时候调下一个
  - 可追溯：每个环节的假设、证据等级、未决问题都被记录下来
  - 不可跳过：scripts/operating_validators.py 检查每个 subagent
  输出是否包含非空的 Assumptions: 字段

  ---
  第四层：独立否决权（Independent Veto）

  这是一个非常精巧的治理设计——规则 03-no-overlap-role-map.md 和
  15-reader-experience-authority.md：

  三个 agent 拥有独立否决权，可以阻止章节推进，且这个否决权不受
  Jerry（调度者）控制：

  ┌────────────────────┬───────────────────────────────┐
  │       Agent        │         否决触发条件          │
  ├────────────────────┼───────────────────────────────┤
  │ Laura（红队编辑）  │ V1/V3/V8 核心读者体验值退化   │
  ├────────────────────┼───────────────────────────────┤
  │ Nancy（法律顾问）  │ Rule-05/07 过度断言或暗示负担 │
  ├────────────────────┼───────────────────────────────┤
  │ the-reader（读者） │ HARD 级别的阅读摩擦           │
  └────────────────────┴───────────────────────────────┘

  否决后只有 xiaolai（主创作者） 可以 override。

  为什么这个设计很重要：Codex 在评审中指出，如果红队和法律审查的"不通过"由推动改
  写的同一个编排者（Jerry）来决定是否采纳，那就存在 kill-switch
  被压制的风险。独立否决权让 Laura 和 Nancy 的 halt authority 不受编排者压力——这
  正是这本书自己诊断的模式（控制权与问责分离），应用到项目自身治理上。

  ---
  第五层：技能（Skills）作为专业知识模块

  29 个技能位于 .claude/skills/，每个是独立的知识模块，可以被多个 agent 复用：

  case-file-method/        — 案例研究方法论
  evidence-grading/        — A/B/C/D 证据分级
  responsibility-chain-mapping/  — 责任链分析
  counterargument-red-team/      — 最强反方论证
  defamation-wording/            — 诽谤风险措辞
  reader-cold-read/              — 冷读测试
  chapter-blueprint/             — 章节蓝图
  ...

  Agent 通过 frontmatter 的 skills: 字段声明自己加载哪些技能。技能不是
  agent——它们不能独立运行，而是给 agent 装载领域知识的模块。

  ---
  第六层：Slash 命令作为用户入口

  10 个 slash 命令在 .claude/commands/，每个都有 owner:
  frontmatter，指向执行它的 agent：

  # .claude/commands/crew-briefing.md
  ---
  owner: jerry-crew-chief
  ---
  /crew-briefing   → 调度 Jerry，产出当前冲刺计划
  /case-file       → 调度 Delon，做案例研究
  /chapter-brief   → 调度 Bonnie，做章节架构
  /source-audit    → 调度 Stephen，审计证据质量
  /red-team        → 调度 Laura，攻击论点
  /proposal-pack   → 调度 Blair，出书提案
  /produce-chapter → 调度 Jerry 编排整章生产流水线

  设计原则：命令暴露给用户的接口很简单，内部自动路由到正确的 agent。

  ---
  第七层：Hook 系统（自动化质量门）

  9 个 Python hook 在 .claude/hooks/，通过 settings.json 注册：

  {
    "SessionStart":   ["session-context.py"],        // 注入当前冲刺状态
    "PreToolUse":     ["guard-destructive-bash.py"],  // Bash 危险操作拦截
    "PostToolUse":    [
      "check-agent-frontmatter.py",  // agent 文件编辑后校验
      "scan-overclaim.py",           // 扫描过度断言词汇
      "scan-implication.py",         // 扫描结构性暗示过载
      "scan-cite-density.py",        // 扫描引用格式违规
      "scan-pronoun-discipline.py",  // 扫描代词违规
      "scan-kdp-epub-css.py"         // 扫描 EPUB CSS 违规
    ],
    "SubagentStop":   ["log-subagent-finish.py"]     // 记录 agent 完成
  }

  这些 hook 是规则的可执行化——规则写在 .claude/rules/ 里，hook
  在每次文件编辑后自动扫描违规项。规则与执行之间形成了闭环。

  ---
  第八层：The Reader——最特别的 Agent

  the-reader 是整个体系里最有创意的设计：

  1. 不在团队中 —— 它是 "deliberately NOT on the crew"
  2. 冷读 —— 不读 brief、不读 case file、不读规则、不读注册表，只看最终章节文本
  3. 只报告体验，不提出修改 —— "我在这里丢了线索" 而不是 "加一句过渡句"
  4. 永远不会错 —— 它的体验是无可辩驳的数据，"我感觉困惑"不需要被论证
  5. 拥有否决权 —— HARD 发现可以阻止章节发布

  这本质上是把可用性测试（usability testing）引入了 AI
  写作流程。被测试者不知道设计意图，只知道产品对自己做了什么。

  ---
  第九层：规则体系（The Constitution）

  .claude/rules/ 下有 16 条规则，形成了项目的 "宪法"：

  00-five-values.md          — 五条最高原则（宪法修正案级别）
  01-case-taxonomy.md        — 四种替罪羊分类
  02-evidence-grades.md      — A/B/C/D 证据等级
  03-no-overlap-role-map.md  — 角色不重叠、否决权
  04-style-guide.md          — 写作风格
  05-overclaim-language.md   — 禁止无引用的断言动词
  06-quote-integrity.md      — 引用完整性
  07-implication-burden.md   — 结构性暗示 = 断言
  08-treatment-class-discipline.md  — 改写分类
  09-rewrite-lifecycle.md    — 改写生命周期
  12-reader-experience-values.md    — 10 个读者体验值
  13-citation-form.md        — Chicago 引用格式
  14-authorial-stance.md     — 作者立场与代词
  15-reader-experience-authority.md — 读者否决权
  16-kdp-epub.md             — Kindle 出版格式

  规则之间有层级：00-five-values.md
  是最高原则，任何其他规则与它冲突时它优先。scripts/sync_five_over_rules.py
  保证五大原则被字节级同步到所有 agent、所有 skill 和所有规则文件中。

  ---
  可迁移的核心模式总结

  如果你要在自己的项目中搭建 agent 体系，以下是最值得复用的模式：

  1. Agent 设计检查清单

  - [ ] 每个 agent 有明确的 Owns / Does not own
  - [ ] tools 是白名单，最小权限原则
  - [ ] maxTurns 按职责复杂度分档
  - [ ] 统一输出 schema（Owner/Task/Assumptions/Handoff）
  - [ ] 包含使用示例（触发条件清晰）

  2. 调度架构

  - [ ] 有向无环图（DAG），深度有限
  - [ ] 有静态校验脚本
  - [ ] 叶子节点不能生成子节点
  - [ ] 异步 Handoff 而非嵌套调用

  3. 治理机制

  - [ ] 独立否决权（检查者不受被检查者控制）
  - [ ] 最终 override 需要命名的人签名
  - [ ] 所有否决记录在案

  4. 质量自动化

  - [ ] 规则 = 文档 + 可执行 hook 双重存在
  - [ ] 每次文件编辑后自动扫描违规
  - [ ] 测试套件验证所有架构约束

  5. "外行人"视角

  - [ ] 有一个角色故意不看内部信息
  - [ ] 只报告原始体验，不提修改方案
  - [ ] 它的体验是不可辩驳的数据

  ---
  这个项目的 agent
  体系最厉害的地方不是数量多，而是每个设计决策都在实践这本书自身的论点——责任不能
  模糊、控制权要清晰、每个决策要签名、检查者不能受被检查者控制。这是一个用 agent
  架构来论证 agent 架构应该怎样设计的递归案例。

  ---
  阶段 2：理解 Skill 的设计模式

  目标：理解 skill 是怎么给 agent 装载领域知识的。

  参考文件：
  - .claude/skills/evidence-grading/SKILL.md — 看一个 skill 的结构
  - .claude/skills/counterargument-red-team/SKILL.md — 看一个方法论 skill
  - AGENTS.md 中的 "Repository layout → Active workspace" 段 — 理解 skill
  如何被扫描

  要弄懂的关键点：
  1. Skill 和 Agent 的关系——Agent 在 skills: 里声明，Skill 本身不知道谁在用
  2. Skill 不是可调用的 agent——它是注入到 agent 上下文中的知识模块
  3. 这个项目的 29 个 skill 可以按功能分类：
    - 方法论类（case-file-method, evidence-grading, counter-case-method）
    - 审查类（citation-hygiene, defamation-wording, implication-audit）
    - 读者测试类（reader-cold-read, reader-experience-sweep）
    - 结构类（chapter-blueprint, scene-construction,

⏺ 这个问题问到了整个项目最值钱的地方。

  ---
  统一原则：控制权必须可追溯

  这本书的核心论点是：

  ▎ 责任洗钱的发生机制 = 控制权与可见性分离。当一个决策可以被归因于"系统""程序""
  ▎ 委员会""市场"而不是一个具体的命名的人时，责任就被洗掉了。

  整个 agent 架构的每一个设计决策，都是在防止这个分离发生在项目内部。书的诊断对
  象和书的生产系统遵循同一套纪律。

  换句话说：架构不是"怎样让 AI 写书更高效"，而是"怎样让 AI 
  参与写书的同时，控制链不被洗掉"。

  ---
  从这个原则出发，推导每个设计决策

  决策 1：每个功能只有一个 Owner

  问题：如果两个 agent 都能"决定这个案例该分到哪一类"，
        出了问题谁负责？→ "那是他的判断" / "我只是建议"

  解决：规则 03-no-overlap-role-map.md 明确规定——

  ┌──────────┬───────────────────┐
  │   功能   │    唯一 Owner     │
  ├──────────┼───────────────────┤
  │ 书的结构 │ Bonnie（只有她）  │
  ├──────────┼───────────────────┤
  │ 章节语言 │ Wayne（只有他）   │
  ├──────────┼───────────────────┤
  │ 事实判断 │ Stephen（只有他） │
  ├──────────┼───────────────────┤
  │ 法律措辞 │ Nancy（只有她）   │
  └──────────┴───────────────────┘

  没有"共同负责"。共同负责 = 没人负责。

  决策 2：调度图深度 ≤ 2

  问题：如果调度链是 Jerry → A → B → C → D，
        当 D 出错时，是 D 的问题还是 B 派活不清楚的问题？
        层数越多，归因越模糊。

  解决：scripts/check_agent_graph.py 强制约束——

  Jerry (depth 0)
    └── 7 个 cell lead (depth 1)
          └── 研究员/专家 (depth 2, 必须叶子)

  两层足够分工，但不够隐藏。超过两层的指挥链本身就是洗责任的温床。

  决策 3：异步 Handoff 而非嵌套调用

  问题：如果 Wayne 写稿时直接调 Nancy 改措辞，
        Nancy 的修改融进了 Wayne 的提交里，
        事后无法区分"这是 Wayne 写的"还是"Nancy 改的"。

  解决：每个 agent 的输出是独立文件 + 强制 schema：

  Owner: Wayne
  Assumptions: <必须非空>
  Handoff: Nancy

  每一步都有签名。每一步的假设都被记录。交接不是发生在代码里（嵌套调用），而是发
  生在文件系统里（显式记录）。异步不是性能优化，是可审计性设计。

  决策 4：检查者独立于被检查者

  问题：如果推动改写的 Jerry 同时决定 Laura 的红队意见是否采纳，
        当 Jerry 急于推进时，Laura 的反对可以被"合理忽略"。

  解决：独立否决权——

  - Laura 的 HARD block → Jerry 不能 override
  - Nancy 的 HARD block → Jerry 不能 override
  - 只有 xiaolai（人类作者）可以 override，且必须记录理由

  这是三权分立的思想：行政（Jerry）不能否决司法（Laura/Nancy）的判决。检查者和被
  检查者放在同一条指挥链里，检查就是表演。

  决策 5：The Reader 故意不知道任何内部信息

  问题：如果你知道这段文字想表达什么，你就读不出读者的真实困惑。
        内部人员永远无法模拟"第一次看到"的体验。

  解决：The Reader——

  - 不读 brief、不读 case file、不读规则
  - 只读和读者看到的一模一样的最终文本
  - 只报告体验（"我在这丢了线索"），不提修改方案
  - 拥有和 Laura/Nancy 同级的否决权

  这是可用性测试的思想移植到了写作流程中。知情 = 污染。冷读是不可替代的数据。

  决策 6：规则双重存在——文档 + 可执行 hook

  问题：如果规则只写在文档里，"遵守"就靠人的记忆和善意。
        当 deadline 压力大时，规则被选择性忽略。

  解决：每条关键规则都有对应的自动扫描——

  ┌──────────────────────────┬───────────────────────────────────────────────┐
  │         规则文档         │                   执行 Hook                   │
  ├──────────────────────────┼───────────────────────────────────────────────┤
  │ 05-overclaim-language.md │ scan-overclaim.py（每次 Write 后扫描 banned   │
  │                          │ verbs）                                       │
  ├──────────────────────────┼───────────────────────────────────────────────┤
  │ 07-implication-burden.md │ scan-implication.py（扫描结构性暗示）         │
  ├──────────────────────────┼───────────────────────────────────────────────┤
  │ 13-citation-form.md      │ scan-cite-density.py（扫描引用格式）          │
  ├──────────────────────────┼───────────────────────────────────────────────┤
  │ 14-authorial-stance.md   │ scan-pronoun-discipline.py（扫描 "you" / "the │
  │                          │  reader"）                                    │
  └──────────────────────────┴───────────────────────────────────────────────┘

  规则如果没有自动执行，就不是规则，是愿望。

  决策 7：宪法 + 自动同步

  问题：如果每个 agent 文件里都手写了五大原则，
        改一个措辞需要手动改 46 个文件。
        必然 drift。必然有人用的是旧版本。

  解决：sync_five_over_rules.py——

  - 宪法源文件只有一个：00-five-values.md
  - 所有 agent/skill/doc 中的五大原则块都是 <!-- GENERATED --> 标注的
  - 改源文件 → 跑脚本 → 全部同步
  - --check 模式在 CI 中跑，drift 直接失败

  一致性不能靠纪律，要靠自动化。

  决策 8：工具白名单 + 无 Bash

  问题：如果一个 agent 可以执行任意 shell 命令，
        它删除文件后，你怎么追溯是哪个 agent 在什么上下文下做的？

  解决：

  - 所有 agent 都没有 Bash 权限
  - 所有 agent 都没有 TodoWrite 权限
  - 工具的分配精确到每个 agent（laura 有 WebSearch，the-reader 没有）

  权限不是按"角色地位"给的，是按"这个角色需要什么才能完成任务"给的。
  最小权限原则。

  决策 9：跨工具兼容

  问题：如果一个工具（Claude Code）出问题，整个流程锁死。

  解决：AGENTS.md 是唯一真相源——

  CLAUDE.md → @AGENTS.md
  GEMINI.md  → @AGENTS.md
  Codex 直接读 AGENTS.md

  三个工具共享同一份上下文，同一个规则体系，同一套 agent 定义（通过 cc-suite
  插件 bridge）。不绑定单一供应商。

  ---
  总结：架构 = 论点的递归应用

  用一句话概括这个架构的设计思路：

  ▎ "谁控制了产出，就必须对产出负责——这个原则不仅适用于书里分析的案例，也适用于
  ▎ 写这本书的流程本身。"

  具体来说：

  ┌────────────────────────┬─────────────────────────────────┐
  │        书的诊断        │           架构的应对            │
  ├────────────────────────┼─────────────────────────────────┤
  │ 责任被洗进"系统"       │ 每个功能只有一个命名的人        │
  ├────────────────────────┼─────────────────────────────────┤
  │ 指挥链太长导致归因模糊 │ 调度深度硬限制为 2              │
  ├────────────────────────┼─────────────────────────────────┤
  │ 程序替代判断           │ 检查者独立于执行者，有否决权    │
  ├────────────────────────┼─────────────────────────────────┤
  │ 内部知识掩盖外部体验   │ The Reader 故意不知情，有否决权 │
  ├────────────────────────┼─────────────────────────────────┤
  │ 规则写在纸上等于不存在 │ 每条规则有对应的自动扫描 hook   │
  ├────────────────────────┼─────────────────────────────────┤
  │ 文档 drift             │ 宪法自动同步到所有文件          │
  ├────────────────────────┼─────────────────────────────────┤
  │ 事后不可追溯           │ Handoff 协议强制每一步签名      │
  └────────────────────────┴─────────────────────────────────┘

  这不是"怎样更好地用 AI"，而是**"怎样用 AI 的同时不被 AI
  洗掉你自己的责任"**。这正是这个项目跟其他"multi-agent
  教程"最根本的区别——它不是在教你怎么指挥 AI，它是在教你怎么在指挥 AI
  的同时，保证你不会变成自己书里批评的那种人。

  决策 10：改写不是二元的——五种治疗等级

  大多数项目的改写只有两种状态：重写 vs 不改。但这个项目有五种：

  ┌─────────────────────────┬────────────────────────┬───────────────────────┐
  │          等级           │          条件          │         成本          │
  ├─────────────────────────┼────────────────────────┼───────────────────────┤
  │ no-change               │ 通过了所有检查，无缺陷 │ 零                    │
  ├─────────────────────────┼────────────────────────┼───────────────────────┤
  │ prose-polish            │ 结构好，句子节奏有问题 │ Wayne 1 轮            │
  ├─────────────────────────┼────────────────────────┼───────────────────────┤
  │ defamation-safe-tighten │ 法律风险措辞需要收紧   │ Nancy + Wayne 各 1 轮 │
  ├─────────────────────────┼────────────────────────┼───────────────────────┤
  │ structural-polish       │ 需要调整场景顺序/视点  │ Bonnie + Wayne +      │
  │                         │                        │ 跨章审计              │
  ├─────────────────────────┼────────────────────────┼───────────────────────┤
  │ full-craft-rewrite      │ 核心价值失败           │ 全流程重来            │
  └─────────────────────────┴────────────────────────┴───────────────────────┘

  关键设计：

  1. no-change 也需要证据——不能因为"没人看过"就说没问题。必须有 defect-map
  证明通过了检查。
  2. 等级是输入不是输出——不是因为"我想重写"就选 full-craft-rewrite，而是因为
  defect-map 证明核心价值确实失败了。
  3. 用具体案例说明为什么等级判断不能凭直觉——规则里给了例子：一个章节有 V6 和
  V10 两个缺陷，"天真读法"会说是
  full-craft-rewrite，但实际上核心价值全部通过，只需要 structural-polish。

  防止了什么：防止了"我觉得这章不好，全部重写"的资源浪费，和"我觉得这章还行，不
  改了"的偷懒。

  决策 11：改写有生命周期，审计历史不可覆盖

  ready → in-rewrite → in-review → ready
                ↑_____________|
                (审计失败时回退)

  关键设计：在覆盖任何审计报告之前，先把旧报告快照存到
  process/audits/history/<chapter>/<timestamp>/。

  process/audits/history/
    02/
      2026-05-27T14-30-00Z/
        audit-chapter.md
        evidence-audit.md
        defamation-wording.md
        ...
      2026-06-04T09-15-00Z/
        ...

  快照永不删除。 改写失败时，可以从快照 + git history 恢复。

  防止了什么：防止了"改写之后发现不如原来的好，但原来的审计记录已经被覆盖了，没
  法回滚"。

  决策 12：每个案例必须配一个"反例"

  这是用 .claude/skills/counter-case-method/SKILL.md 定义的硬要求：

  ▎ 书中的每个替罪羊案例，必须配一个同一洗钱模式中被拦截、逃脱或揭穿的反例。

  反例不是"好结局"。反例是一个有名字、可迁移的拦截机制——举报人、独立调查、技术验
  证、法庭、持久公民社会压力——而且要诚实记录逃脱的代价（花了多少年、多少代价、在
  被逆转前吸收了多大伤害）。

  明确禁止三件事：
  - "靠运气逃脱"不能作为反例（不可迁移）
  - "公众愤怒"或"媒体关注"不能作为拦截机制（没有命名的制度性行动者）
  - 反例的洗钱模式必须和配对的替罪羊案例一致（不一致则教训不成立）

  防止了什么：防止了书变成一本"世界很糟糕"的绝望目录。也防止了廉价的乐观——"总会
  有正义的"不算反例，只有"这个特定的机制在什么条件下起了作用"才算。

  ---
  决策 13：跨章节登记表——追踪 13 章之间的承诺

  一本书有 13 章，Chapter 1 里埋的线索要在 Chapter 11 里回收。如果各章由不同的
  agent 在不同时间写，谁负责追踪？

  答案是四个登记表文件 book/registries/：

  callback-graph.yml     — 22 条跨章节呼应（"前面提过的枪，后面必须响"）
  cognitive-arc.yml      — 50 个概念的引入-发展-回收路径
  motif-registry.yml     — 9 个贯穿全书的意象（如 "the-altar" 有禁区规则）
  treatment-classes.yml  — 每章的改写等级

  这本质上是契诃夫法则的执行系统："如果你在第一章展示了一把枪，它必须在第三章开
  火。"

  Chekhov 验证报告（process/audits/chekhov-verification-2026-05-30.md）就是对这
  三个登记表的全面审计：

  22 条 callback 边 → 全部双端点存活
  9 个 motif → 干净，包括高风险禁区 "the-altar" 无泄漏
  50 个 cognitive-arc 项目 → 49/50 通过
  11/13 章的 fair clue 测试通过

  防止了什么：防止了"多 agent 异步写 13
  章"变成"各写各的，前后矛盾，埋的线索没人收"。

  ---
  决策 14：会话状态持久化——SessionStart Hook + STATUS.md

  每次新开一个 Claude Code
  会话，模型的上下文是空的。它不知道上次做到哪了。怎么保证连续性？

  SessionStart hook
    → 读取 .claude/state/current-focus.md
    → 作为 additionalContext 注入到系统提示词
    → 每个新会话一打开就直接看到当前冲刺状态

  current-focus.md 里记录了：
  - 当前冲刺目标
  - 待办项和 owner
  - 法律重审的到期时钟（"2026-06-24 Nancy 重审 ch-02"）
  - 23 个未解决的 [EVIDENCE NEEDED] 标记

  STATUS.md 则是一个更完整的仪表板——13 章的 gate-by-gate 进度表。

  防止了什么：每次新对话都要花半程时间回忆"上次做到哪了"。也防止了"某个到期检查
  没人记得"。

  决策 15：法律审查不是一次性的——到期时钟

  项目里有明确的重审时钟：

  2026-06-24 — Nancy 30-day re-pass on ch-02 slot 8 (Ukrainian children)
  2026-06-25 — Nancy 30-day re-pass on ch-8 (Iraq WMD), ch-9 (live political
  content),
               ch-10 (live AI litigation), ch-12 (FRA / DOGE / live records
  litigation)

  凡涉及仍在进行的诉讼、在世人物、活跃冲突的章节，法律审查有一个过期时间。30
  天后必须重新审查，因为法律状态可能已经变了——某个人可能被起诉了、某个案子和解了
  、某个说法从事后看变成了诽谤。

  防止了什么：防止了"出版时法律审查是通过的，但出版时案件状态已经变了"。

  决策 16：三层引用模型——每层服务不同的读者

  规则 13-citation-form.md 定义了三层引用：

  ┌────────┬──────────────┬─────────────────┬───────────────────────────────┐
  │   层   │     载体     │      读者       │             例子              │
  ├────────┼──────────────┼─────────────────┼───────────────────────────────┤
  │        │              │                 │ "The Senate Armed Services    │
  │ 1.     │ 句子里的来源 │ 读者 +          │ Committee inquiry,            │
  │ 散文中 │ 身份         │ 有声书听众      │ declassified April 2009,      │
  │        │              │                 │ concluded that..."            │
  ├────────┼──────────────┼─────────────────┼───────────────────────────────┤
  │ 2. 行  │ [CITE:       │ 编译步骤、审阅  │ [CITE: taguba-report-2004]    │
  │ 内标记 │ card-slug]   │ 者              │                               │
  ├────────┼──────────────┼─────────────────┼───────────────────────────────┤
  │ 3.     │ Chicago NB   │ 翻到末尾的读者  │ 完整的作者-标题-出版信息-页码 │
  │ 尾注   │ 完整引用     │ 、学者          │ -存档链接                     │
  └────────┴──────────────┴─────────────────┴───────────────────────────────┘

  关键约束：
  - 行内 [CITE:] 只能包含 slug，不能放 URL、不能放逗号、不能放 "see also"——≤60
  字符
  - 第 1 层的来源命名必须保证听有声书的人也能知道信息从哪来
  - URL 验证是内部质量检查，绝对不印在尾注里（不要 (verified 2026-05-28)
  这种噪音）

  防止了什么：防止了"引用有，但读者不知道；尾注完整，但听有声书的人完全不知道来
  源；行内标记变成 200 字符的微型参考文献，打乱阅读节奏"。

  决策 17：MaxTurns 不是状态排名，是"这个角色需要多少轮才能完成判断"

  ┌─────────────────────────┬─────────┬─────────────────────────────────────┐
  │          Agent          │ MaxTurn │                理由                 │
  │                         │    s    │                                     │
  ├─────────────────────────┼─────────┼─────────────────────────────────────┤
  │ Jerry                   │ 40      │ 需要跨 cell                         │
  │                         │         │ 排序、解决冲突、最终路由            │
  ├─────────────────────────┼─────────┼─────────────────────────────────────┤
  │ Bonnie/Wayne/Stephen/La │ 25      │ 多步规划/修订循环                   │
  │ ura                     │         │                                     │
  ├─────────────────────────┼─────────┼─────────────────────────────────────┤
  │ Nancy/Blair             │ 20      │ 中等深度，有明确闸门                │
  ├─────────────────────────┼─────────┼─────────────────────────────────────┤
  │ 研究员/Alan             │ 18      │ 需要迭代检索但权限更窄              │
  ├─────────────────────────┼─────────┼─────────────────────────────────────┤
  │ xiaolai                 │ 20      │ 判断应该紧凑；如果争论太久，应该升  │
  │                         │         │ 到真人                              │
  └─────────────────────────┴─────────┴─────────────────────────────────────┘

  设计思路：MaxTurns
  不是按"谁更重要"给的。是按**"这个角色的决策需要多少轮来回才能完成"**。研究员
  18 轮够了，因为检索和建案例文件不需要复杂博弈。Jerry 40 轮，因为协调 7 个 cell
  lead 需要大量路由判断。xiaolai 只有 20 轮——故意限制，因为"如果这个判断在 20
  轮内说不清楚，它应该升到真人作者而不是被 AI 争论到天荒地老"。

  ---
  决策 18："no-change 也需要证据"

  这其实值得单列。规则 08 里有一条：

  ▎ "A chapter cannot be classified no-change because no one looked at it; 
  ▎ defect-map must exist and show passing values."

  大多数流程里，"不改"是默认状态。但这个项目把不改变成了一个需要论证的决策——你必
  须证明你看过了，证明了它通过了检查，才能决定不改。

  防止了什么：防止了最隐蔽的责任洗钱——"我们没动它，所以没问题。出事了？那是之前
  做的，和我们这次 sprint 无关。"

  ---
  决策 19：反身性——在审计报告里发现自己的洗钱

  Chekhov 验证报告里有一段非常能说明问题：

  ▎ "a placeholder for principal-author judgment was apparently resolved without
  ▎ an authoring record, and the outstanding-work list still shows it open. 
  ▎ That is exactly the substitution pattern the book diagnoses — at micro 
  ▎ scale, inside the book's own production process."

  决策 21：命令契约——owner 必须 dispatch 自己

  决策 24：波浪式生产——并行只在 DAG 允许时使用

  生产不是 13 章一条线做完，也不是全部并行。是四波：

  Wave 1: ch-3 → ch-1（顺序——ch-3 解锁诊断工具，ch-1 最后写以对齐语调）
  Wave 2: ch-4,5,6,7（并行研究 + 并行 draft，但各自独立走 gate 序列）
  Wave 3: ch-9 → ch-10 → ch-8（研究并行，但 draft 和 gate 严格按阅读顺序）
  Wave 4: ch-11 → ch-12 → ch-13（严格顺序——每章消费前一章）
  Wave 5: 编译 + 提案包

  顺序和并行的选择不是凭直觉，是由章节依赖 DAG 决定的：ch-3
  是所有后续章的工具箱，所以第一波；Part II 的四章互不依赖，所以可以并行；Part
  III 有指定的阅读顺序（9→10→8），所以 draft 按顺序。

  决策 27：Surrogate 模式——AI 模拟作者思维但不持有作者权力

  xiaolai agent 的定位非常精确：

  ✅ 可以做的：应用六条元价值观判断一个具体的 crew 决策
  ❌ 不能做的：commit、push、scope 扩展、预算/模型变更、
              作者个人偏好（风格、品味、封面署名）

  它的默认响应 schema 里有一个特别的字段：

  Surface-to-principal items: <任何超出你权限的事，哪怕只是部分>

  而且它有一条明确的规则："When in doubt: surface, do not decide."

  设计思路：当 AI 能模拟你的判断框架时，最危险的不是它判断错了，而是它替你做了不
  该替的决定。Surrogate 模式把"推理"和"授权"分开——它帮你推理，但拒绝替你授权。

  决策 29：图表也是证据，走同样的审查门

  规则 03 明确规定，图表、表格、责任链图不是"美术部的免检产品"。一张图表的每个数

  决策 30：[EVIDENCE NEEDED] 不阻塞 ready，但阻塞 galley

  book/STATUS.md 里记录了 23 个未解决的 [EVIDENCE NEEDED] 标记。但所有 13 章都在
  status: ready。

  这是故意的设计：

  ready ≠ 可以出版
  ready = 可以进入出版准备流程
  galley lock = 可以出版

  证据缺口可以容忍在 ready
  阶段（因为"找到更好的来源"不应该阻塞写作流程），但不能容忍在 galley lock
  阶段（因为出版时不能有未解决的证据）。

  防止了什么：防止了完美主义瘫痪——"这个来源还不够好，所以这章不能推进"。也防止了
  反向的偷懒——"反正已经 ready 了，证据缺口就放着吧"。两个门有不同的严格度。

  决策 32：强调标记审计——连斜体和粗体都有纪律

  scripts/audit_emphasis.py 和 test_audit_emphasis.py
  做了一件很小但很能说明问题的事：审计章节中每一个 <em> 和 <strong> 标记。

  它分类：
  - logical_table：表头加粗 ✓
  - logical_publication：书名斜体 ✓
  - logical_install_first：首次引入术语加粗 ✓
  - decorative_intensifier：纯粹为了"加重语气"的加粗 ✗

  决策 33-38：来源分类账——证据作为数据库

  33. 292 张卡片是数据库，不是参考文献列表

  每张卡片不是"一条引用"，而是一个结构化的证据记录：

  id · source 元数据 · claim 原文 · evidence_grade + grade_rationale
  verification_log（多步骤，每步有 actor + timestamp + outcome）
  url_check（primary + Wayback，HTTP 状态码，verifier_checkpoint）
  defamation（living_subjects, nancy_cleared, 日期, 备注）
  dispute（contested/uncontested, 具体争议内容, carry-forward 指令）
  provenance（created_by, created_on, superseded_by）
  body_sha256（加密哈希）

  292 张卡片，1.3MB 结构化证据元数据。

  34. 每张卡片有 SHA-256 哈希

  body_sha256 字段。证据数据库具有加密级别的完整性。卡片被篡改可以被检测。

  35. 验证日志按 actor 归因

  每一步验证记录：谁做的（stephen）、什么时候、什么结论（PASS/PARTIAL/B）、什么
  备注。审计追踪精确到单个 agent 的单个操作。

  36. URL 可达性标注验证者位置

  verifier_checkpoint: principal-author-cn——承认 URL
  可达性取决于验证者的网络位置。证据元数据本身包含验证条件的声明。

  37. 争议追踪带 carry-forward 指令

  dispute.status: contested 不只是标记，还带具体说明（"在 pin-cite 层面
  contested"）和行动指令（"PACER exhibit lock before final manuscript
  freeze"）。卡片携带了解决争议所需的具体操作。

  38. 诽谤审查在卡片层面做

  每张卡片有 defamation 块：列出了涉及的活人、Nancy
  审查日期、是否通过。法律审查不在章节层面，在每张证据卡片层面。

  决策 39-47：从源到产品的管道

  39. EPUB 是编译产物，绝不直接编辑

  源是 v6 章节 + spine 配置。EPUB 是构建输出。构建在存在未解析 [CITE:]
  标记时硬失败。源和产物的分离是绝对的。

  40. 书脊是独立的 YAML 配置

  spine-v6.yml——阅读顺序与章节内容解耦。重排顺序不需要编辑散文。front-matter
  条目可标记 optional: true（空的 dedication 不生成占位页面）。

  41. 同一源 → 两个版本管道

  v6 规范文本 → 可重排 EPUB（Kindle）+ 固定布局 6×9 打印 PDF（KDP 平装本，446
  页），通过独立的确定性管道。修复一次，两个版本同时更新。

  42. Kindle Previewer 是 epubcheck 之上的权威关卡

  epubcheck 验证规范一致性；Kindle Previewer 3
  验证实际设备渲染。"一个文件可以通过 epubcheck 但在 Paperwhite 上崩溃。"

  43. 部分分隔符是 EPUB 中唯一的内页图片

  明确约束：固定布局的 dossier
  内部页面在可重排中不可存活。限制被承认并接受，不做 hack。

  44. 脚本 ≠ Agent 的明确边界

  确定性转换（构建、编译、验证）用 Python/JS 脚本。需要判断的工作用
  agent。不会让 agent 做 pandoc 能做的事。

  45. URL 归档作为构建步骤

  verify_card_urls.py + wayback_capture.py
  主动归档即将消失的页面。验证时间戳只存在于卡片上，绝不印在正文中——"(verified
  2026-05-28)"对读者是噪音。

  46. EPUB 脚注作为弹出窗口

  要求 epub:type="noteref" / epub:type="footnote"
  标记，使注释弹出而不是内联渲染。读者体验在标记级别被考虑。

  47. 部分分隔符图片带 alt 文本

  可访问性设计在管道里，不是事后补救。

  决策 48-55：读者体验的系统性设计

  48. 读者状态阶梯

  toc.yml 不只是目录，定义了认知进阶：

  S0（可见替罪羊）→ S1（诊断觉醒）→ S2（模式安装）
  → S2.5（模式压力测试）→ S3（可操作）

  每个 Part 声明 reader_state_in、reader_state_out 和一个 act_reversal（旧信念 →
  新信念）。这不是"这章写得好不好"，而是"这章完成了读者状态的转换没有"。

  49. 双受众引用设计

  第 1 层（散文内命名来源）为有声书听众服务——他们不能翻到尾注。第 3
  层（尾注）为学者服务。设计承认不同受众对来源的访问方式不同。

  50. "A Note on Cases" 作为读者-法律合同

  第一章之前明确声明：不是党派的、不是西方中心的、案例选择是因为责任链记录存在。
  先发制人处理偏见指控。承认"三个章节反复回到 Donald
  Trump"，解释这不是编辑选择而是公共记录。

  51. "Cases at a Glance" + "Acronyms and Institutions"

  后记中的快速参考工具——读者不必在 13 章中记住每个案例和每个缩写。

  52. 作者的注释放在最后

  ▎ "placed last so the reader earns the right to ask 'why and how' only after 
  ▎ reading the book."

  AI
  装置的披露是被赢得的——读者先遇到论点，然后才被告知论点是如何生产的。不前置。

  53. "Note on Sources and Method" 与 "Note from the Author" 分开

  技术性披露（方法论）和个人性披露（动机）是两个文件。不同受众，不同署名，不同语
  调。

  54. 部分分隔符标语

  每个 Part 有 tagline：
  - Part I: "Four shapes. Eight questions. One instrument."
  - Part II: "Pattern, not period. The mechanism is the villain."
  - Part III: "Modern complexity is the design. The diagnostic still works."
  - Part IV: "Three rules to carry. The diagnostic, made portable."

  为部分转换增添了叙事分量。

  55. EPUB 封面需求明确到像素

  2,560×1,600 px，1.6:1 比例，RGB/sRGB，≥300 DPI。不模糊、不推测。封面是预发布
  checklist 中的一项显式阻塞项。

  决策 56-63：制度记忆与反熵

  56. Agent 持久化记忆目录

  每个 agent 有 .claude/agent-memory/<name>/。决策跨会话存活。Jerry
  的记忆存储了章节排序决策；Bonnie 的存储了结构约束。这是 agent 的"制度记忆"。

  57. STATUS.md 自我文档化

  STATUS.md 包含自己的使用说明（"How to use this file"）。任何打开它的 agent
  都知道如何读取和更新它。元数据文件是自我记录的。

  58. 跨领域项目表

  定时重新审查、组合扫描、galley-pass
  项目——不属于任何单一章节的项目有独立的跟踪表。没有"不知道该放哪"的项目。

  59. 退出条件作为可检查清单

  书有一个显式的"完成"定义，包含 ✓ 和 open
  项目。不是主观的。不是"感觉差不多了"。可证伪。

  60. 版本清理作为显式操作

  v6 剪裁时：v1-v5 归档、死脚本退役、过时 hook 移除、settings.json
  修剪。项目明确管理自己的熵。不让 cruft 积累。

  61. 更正标准与生产标准镜像

  "更正需要至少与书中所载一样好的引用。PR
  将按照原始章节所经过的相同关卡进行审查。"更正机制的纪律与原始生产相同。

  62. 图表验证器存在性测试

  test_agent_tool_minimums.py 检查 validate_diagram_artifact.py
  是否存在——因为早期的 agent（Jade）被移除了，但验证能力必须保留。即使相关的
  agent 消失，能力不能随之消失。

  63. 颜色编码 agent

  每个 agent 有 color: 字段。在终端输出中提供视觉区分。会话中容易追踪谁在说话。

  决策 64-70：元级别的纪律

  64. 每张卡片出处追踪

  provenance: created_by, created_on, 
  superseded_by。谁创建了这张卡片？它是否被替换过？替换链是显式的。

  65. 引用格式：芝加哥基准 + 项目特定覆盖

  芝加哥 NB 是基准，但在芝加哥模糊的地方有项目级覆盖（推文、社交媒体）。权威性与
  实用主义结合。

  66. NLPM 提交前关卡

  每次提交需要 NLPM 评分通过。质量评分不是偶尔运行的，是集成到提交工作流的。

  67. 侧车 as_of 版本控制

  来源分类账侧车携带 as_of: 日期。章节无法在侧车过期时返回到 status: ready。Hook
  捕获不匹配。

  68. optional: true 的 front/back-matter

  空的 dedication、epigraph、about-the-author
  不生成占位页面。构建产物绝不包含未填充的内容。没有"[Coming Soon]"页面。

  69. 案件注释中的聚合披露

  "Three of the live-content chapters do return repeatedly to Donald Trump — the
  same person, in two presidencies separated by a single term. That recurrence
  reflects the underlying record."先承认偏见的外观，然后解释为什么不是偏见。

  70. 反身性贯穿始终

  从 Chekhov 审计发现自己的生产过程洗掉了最终句的签字记录，到案件注释承认特朗普
  的反复出现是公共记录的结果而不是编辑选择——这个项目最根本的设计原则是：书诊断的
  任何模式，书的生产系统都必须接受同样的审查。

⏺ 主线其实只有一句话，但这句话你必须理解透——

  ---
  主线：可追溯性（Traceability）

  任何时候、任何人（包括五年后的你自己）问：

  "这个结论是谁做的？基于什么证据？在什么假设下？
   当时有没有人反对？反对意见是怎么被处理的？"

  → 答案必须在文件系统里，不需要问任何人。

  这 70 个决策没有一个是"为了提高效率"。每一个都是在回答：这个环节如果失控了，事
  后还能不能追溯到谁做的决定？

  ---
  推导链：从主线到所有决策

  你不需要记 70 个决策。你只需要在每一个设计节点问自己同一个问题：

  关卡 1：这个产出有 Owner 吗？

  问题：如果出了问题，谁知道该找谁？

  → 每个功能只有一个 Owner（决策 1）
  → 调度深度 ≤ 2，层数多了归因模糊（决策 2）
  → 每个 agent 明确 Owns / Does not own
  → 交接必须写在 Handoff: 字段里，不发生在嵌套调用栈里（决策 3）
  → 每个产出有 Assumptions: 字段，强制非空

  关卡 2：Owner 的决策有能力被推翻吗？（如果不能，Owner 就是独裁者）

  问题：如果 Owner 错了，谁来阻止？

  → 检查者独立于执行者——审查者不能被推动者控制（决策 4）
  → 独立否决权——Laura/Nancy/Reader 对质量有 halt authority
  → 否决必须记录在案；override 必须由 xiaolai 签名
  → 最终判断者（xiaolai surrogate）在指挥链外，有 crew_exempt（决策 28）

  关卡 3：规则怎么保证被遵守？（不能靠人的记忆和善意）

  问题：如果没有自动执行，规则是不是只存在于文档里？

  → 每条关键规则配一个扫描 hook（决策 6）
  → 宪法改一处，脚本同步所有文件（决策 7）
  → 每张卡片有 SHA-256 哈希（决策 34）
  → 每步验证有 actor + timestamp + outcome（决策 35）
  → 架构约束全部有对应测试（决策 25）

  关卡 4：如果改坏了，能回去吗？

  问题：改写之后发现不如原来的好，怎么办？

  → 审计快照在覆盖前存档，永不删除（决策 11）
  → 改写有显式状态机：ready → in-rewrite → in-review → ready（决策 11）
  → 五种治疗等级——不盲目全改或全不改（决策 10）
  → 章节有版本号（v1-v6），旧版本归档不删除（决策 60）
  → 侧车 as_of 版本控制——过期侧车阻塞章节推进（决策 67）

  关卡 5："没人看过"是不是被当作"没问题"？

  问题：no-change 是因为通过检查了，还是因为没人看？

  → no-change 也需要证据——defect-map 必须存在且显示通过（决策 18）
  → The Reader 冷读——故意不知道设计意图，只报告真实体验（决策 5）
  → Chekhov 审计验证跨章承诺——callback/motif/cognitive-arc 全部审计（决策 13）
  → 反身性审计——生产系统本身也必须接受同样审查（决策 31）

  关卡 6：证据链完整吗？

  问题：每个 claim 能追溯到原始文档的具体段落吗？

  → 292 张卡片，每张有：claim 原文 / evidence grade / 验证日志 / URL 状态 /
  争议追踪（决策 33-38）
  → 三层引用——有声书听众和学者各得其所（决策 16）
  → 引用格式有芝加哥基准 + 项目覆盖（决策 65）
  → URL 归档作为构建步骤，防止链接失效（决策 45）

  关卡 7：跨章节的一致性怎么保证？

  问题：13 章各写各的，前后矛盾了谁知道？

  → 四个登记表追踪跨章承诺（决策 13）
  → Chekhov 验证审计：22 条 callback / 50 个概念 / 9 个 motif（决策 13）
  → 术语管控 R51——同义词被标记（决策 22）
  → 读者状态阶梯——每章必须推动读者认知前进（决策 48）

  关卡 8：时间会改变事实，怎么处理？

  问题：出版时涉及活人的案例，法律状态可能已经变了

  → 法律重审到期时钟——30 天后必须重新审查（决策 15）
  → 争议追踪带 carry-forward 指令（决策 37）
  → [EVIDENCE NEEDED] 不阻塞 ready 但阻塞 galley（决策 30）
  → 退出条件可检查——不是"感觉完成了"（决策 59）

  用这条主线去读任何文件

  以后你打开这个项目的任何文件，问三个问题就够了：

  1. 这个文件的存在，是为了让什么东西"可追溯"？
  2. 如果缺了这个文件，什么环节会失去控制？
  3. 它和主线的关系是什么？（是"保证有
  Owner"？还是"保证规则被执行"？还是"保证改坏了能回去"？）

  这就是主线——可追溯性不是附加功能。可追溯性就是架构本身。

  机制 1：Agent Frontmatter 作为可解析的配置

  不是"文档里写了每个 agent 有什么权限"。而是 frontmatter 的 tools: 字段直接被
  Python 正则解析。

  agent 文件里的声明：
  # .claude/agents/laura-red-team-editor.md
  tools: Read, Write, Edit, Grep, Glob, WebSearch, WebFetch
  model: opus
  maxTurns: 25

  脚本读取并校验：
  # scripts/check_tool_grants.py 核心逻辑
  name, tools = parse_agent_tools(agent_path)
  policy = load_policy(policy_doc)

  # 检查 1：策略文档说 Bash=no，frontmatter 必须没有 Bash
  if policy[name].bash == "no" and "Bash" in tools:
      errors.append(f"{name} has Bash but policy says Bash=no")

  # 检查 2：策略文档说授予了 WebSearch，frontmatter 必须有
  for tool in policy[name].targeted_additions:
      if tool not in tools:
          errors.append(f"{name} promised {tool} but it's absent")

  测试确保校验本身不被绕过：
  # tests/test_tool_grants_policy.py
  def test_unexpected_bash_grant_is_flagged(self):
      # 构造一个 frontmatter 里有 Bash 但策略文档说 no 的场景
      # 断言 check_tool_grants.check_repo 返回 errors

  同样的模式应用到所有 frontmatter 约束：
  - test_model_policy.py → 解析 model: 字段，断言全部是 opus
  - test_command_contracts.py → 解析 owner: 字段，断言指向真实 agent
  - check_agent_graph.py → 解析 tools: Agent(...) 调用，构建 DAG，查环、查深度
  - check-agent-frontmatter.py hook → 每次 Write/Edit 后解析 YAML 结构

  机制 2：Hook 管道 (settings.json → Python → stdin/stdout)

  Hook 不是"建议"。Hook 是每次文件编辑后自动运行的 Python 进程。

  注册（.claude/settings.json）：
  {
    "PostToolUse": [{
      "matcher": "Write|Edit|MultiEdit",
      "hooks": [{
        "type": "command",
        "command": "python3 
  ${CLAUDE_PROJECT_DIR}/.claude/hooks/scan-overclaim.py",
        "timeout": 10
      }]
    }]
  }

  执行（.claude/hooks/scan-overclaim.py）：
  # 从 stdin 读取 JSON，检查被编辑的文件内容
  # 搜索 banned verb 模式（knew / deliberately / lied / proves / clearly）
  # 输出 JSON 到 stdout：{decision: "block"|"warn", ...}

  关键：Hook 脚本是被 Claude Code 的运行时调用的，不是被 agent 调用的。Agent
  不能跳过 hook。即使 agent 想写一个包含 knew 的句子，hook
  会在文件写入后立即触发——agent 会看到 hook 的警告输出。

  当前项目有 7 个 PostToolUse hook 同时生效：
  scan-overclaim.py     → 扫描 banned verbs
  scan-implication.py   → 扫描结构性暗示
  scan-cite-density.py  → 扫描引用格式
  scan-pronoun-discipline.py → 扫描代词违规
  scan-kdp-epub-css.py  → 扫描 EPUB CSS 违规
  check-agent-frontmatter.py → 校验 agent 文件 YAML

  每次保存一个章节文件，这 6
  个扫描器同时运行。任何一个发现问题，输出中都会包含警告。

  evidence_grade"，但不能检查"这个 B 级是否真的应该是 B 而不是 A"。后者依赖
  agent 自身的纪律和人工审查。

  第三类：纯人类判断（不可自动化）

  这类必须由人来做。没有任何代码能代替。

  ┌─────────────────────────────┬─────────────────┬──────────────────────────┐
  │            约束             │     执行者      │     为什么不能自动化     │
  ├─────────────────────────────┼─────────────────┼──────────────────────────┤
  │ 书的论点是否正确            │ xiaolai（人类） │ 这是判断，不是模式       │
  ├─────────────────────────────┼─────────────────┼──────────────────────────┤
  │ ch-13 最终句用哪个版本      │ xiaolai（人类） │ 品味问题，不是对错       │
  ├─────────────────────────────┼─────────────────┼──────────────────────────┤
  │ 一个案例该分到哪个分类      │ xiaolai（人类） │ 需要判断不确定性         │
  ├─────────────────────────────┼─────────────────┼──────────────────────────┤
  │ 伊拉克章节的落点            │ xiaolai（人类） │ 政治/伦理判断            │
  ├─────────────────────────────┼─────────────────┼──────────────────────────┤
  │ Laura 的否决是否被 override │ xiaolai（人类） │ 需要签字负责             │
  ├─────────────────────────────┼─────────────────┼──────────────────────────┤
  │ 全书终读                    │ xiaolai（人类） │ 唯一能对最终产物负责的人 │
  └─────────────────────────────┴─────────────────┴──────────────────────────┘

  作者注记里写得很清楚：

  ▎ "What the crew could not do was decide what the book was for. Or what the 
  ▎ four shapes were. Or whether a given case was a pure scapegoat or a partial 
  ▎ one. Or whether the chapter on Iraq should land as it does. ... Those were 
  ▎ judgments under uncertainty, and judgments under uncertainty did not 
  ▎ delegate. I made them."

  ---
  所以真正的架构是三层

  第一层（代码）：强制模式匹配的规则
    → 写错了词、少了字段、图里有环 → 机器拦截

  第二层（Agent 自治 + 代码抽查）：Agent 遵循系统提示词的纪律
    → 机器检查产出物完整性，但判断质量依赖 agent 本身

  第三层（纯人类）：判断不确定性
    → 不可委托的决策，人做，人签字

  这三层叠在一起才是完整的体系。第一层省掉了人检查机械性错误的时间，第二层把可委
  托的智力工作规模化，第三层保证最终签字的人仍然对产物负责。

  代码不是万能的。但凡是能用代码拦截的错误，就不应该让人来发现。 这是这个项目实
  现哲学的核心——代码守住所有能自动化的关卡，人的注意力留给代码守不住的判断。

⏺ 这个问题是在追问我的推理方法。坦白说，我刚才分类时的思考角度是——

  "谁在做验证？这个验证者有能力验证这类东西吗？"

  ---
  推导过程

  从你问"每层都是代码控制的吗"那一刻，我意识到你发现了一个矛盾：70
  个决策，只有一部分有对应的 Python 文件。那没有代码的那些呢？

  于是我反过来推：不是看"有哪些决策"，而是看"验证每个决策需要什么样的验证者"。

  决策："所有 agent 用 opus"
    → 验证方式：读 frontmatter，匹配字符串 "model: opus"
    → 验证者：一段 Python 正则
    → 机器能做 ✓

  决策："Wayne 的散文没有过度断言"
    → 验证方式：扫描 banned verbs（knew/lied/proves/clearly）
    → 验证者：一段 Python 模式匹配
    → 机器能做一部分——但只能抓词汇，抓不了语气和叙事结构
    → 更深的验证：Agent 自身遵循系统提示词中的纪律
    → 验证者：Wayne agent（自律）+ Laura agent（红队）
    → 机器不能完全做 ✗

  决策："伊拉克章节的落点"
    → 验证方式：？？？
    → 不存在客观标准
    → 验证者：只有人类作者
    → 机器不能做 ✗✗✗

  三个类别不是预设的。是按"能做验证的验证者是谁"自然分出来的：

  ┌────────┬────────────────────────────────┬────────┐
  │ 验证者 │           能验证什么           │ 对应层 │
  ├────────┼────────────────────────────────┼────────┤
  │ 代码   │ 模式、结构、字段完整性、格式   │ 第一层 │
  ├────────┼────────────────────────────────┼────────┤
  │ Agent  │ 内容质量、论证强度、措辞适当性 │ 第二层 │
  ├────────┼────────────────────────────────┼────────┤
  │ 人类   │ 判断不确定性、品味、伦理落点   │ 第三层 │
  └────────┴────────────────────────────────┴────────┘

  ---
  这个角度的来源

  这个角度本质上是这本书自己的诊断工具，应用到验证体系本身：

  ▎ 书的八问诊断第 4 问：Who knew or should have known?
  ▎ 第 6 问：Who controlled the record?

  翻译到验证体系上就变成了：

  - 这个验证者有能力知道被验证的内容是对是错吗？
    - 正则表达式能"知道" opus ≠ sonnet，但不能"知道"一个论点是否过度断言
    - Agent 能"知道"措辞不当，但不能"知道"作者真正想说什么
  - 验证权和控制权在谁手里？
    - 如果所有验证都由代码做 → 代码成了最终的真相裁定者（但它不是）
    - 如果所有验证都靠人 → 人成为瓶颈，规模上不去
    - 正确的分配：代码做它能做的，Agent 做代码做不了的，人做人不能委托的

  ---
  换句话说

  这个三层分类不是从"架构设计的角度"得出的。是从**"谁有能力验证什么"这个认知论问
  题**中自然掉出来的。每种验证者有自己的能力上限，上限决定了它该守哪道门。

  而认知论问题本身，就是这个项目最根基的设计直觉——可追溯性的前提是，每一步的验证
  者有能力验证它声称能验证的东西。
  把验证权交给没有验证能力的验证者，就是这本书自己诊断的洗钱模式。

✻ Churned for 32s

❯ 如果从0开始做这个项目，应该先做什么，后做什么？                               

  Thought for 13s (ctrl+o to expand)

⏺ 有个反直觉的答案：不是先建架构。是先做一章。

  ---
  正确的构建顺序

  Phase 1: 冷启动（一个人，零 agent）
    ├── 1. 写出论点的一句话版本
    ├── 2. 用手工方法做完一个完整案例的分析
    ├── 3. 从案例中提炼出规则
    └── 4. 写出第一条无法容忍的错误

  Phase 2: 单 Agent 验证（一个人 + 一个 agent）
    ├── 5. 把规则写成 agent 可执行的系统提示词
    ├── 6. 让一个 agent 重做同一个案例
    ├── 7. 人对比例子的输出和 agent 的输出
    └── 8. 找到 agent 犯的错误 → 加到规则里

  Phase 3: 第一条 Pipeline（多 agent 串联）
    ├── 9. 加第二个 agent（核查第一个 agent 的产出）
    ├── 10. 人对比两个 agent 各自看到的问题
    ├── 11. 定义 Handoff schema
    └── 12. 跑通一整章

  Phase 4: 规模化（从一章到全书）
    ├── 13. 从第二章中发现哪些规则是全局的 → 提炼为宪法
    ├── 14. 根据第三章的需求加新 agent 类型
    ├── 15. 写第一个 hook（当手工检查发现自己总是抓同一种错误时）
    └── 16. 写第一个测试（当 hook 逻辑变复杂需要验证时）

  Phase 5: 收尾
    ├── 17. 编译、出版、法律审查
    └── 18. 清理、归档、版本剪裁

  ---
  为什么不是先建架构？

  因为架构是在做具体案例的过程中长出来的，不是先画好再填充的。

  证据就在这个项目的时间线里：

  2026-05-25  冷启动包生成——先有论点、分类、案例矩阵
  2026-05-27  五大原则被提炼并同步到所有文件
  2026-05-28  第二章完成并达到 ready（proof-of-shape）
  2026-05-30  v6 剪裁，13 章全部 ready

  从冷启动到 proof-of-shape 只花了 3 天。但在此之前有
  dev-docs/04_ARCHIVE_SUPERSEDED_OR_REFERENCE/——一个更早的 workspace，"different
  crew names, different rule numbering"。说明架构被推倒重来过。

  如果你一开始就建了完整的 15 agent + 29 skill + 16 rule
  架构，你会花两周建一个你还没验证过是否正确的系统。然后发现第一个案例就暴露了架
  构的致命缺陷，全部推倒重来。

  先做一章，让架构从那一章里长出来。

  ---
  Phase 1：冷启动——最关键的四步

  第 1 步：写出论点的一句话版本（30 分钟）

  不能是"我要写一本关于 XX 的书"。必须是：

  ▎ "文明没有停止牺牲替罪羊，只是换了祭坛。从祭司到官僚到算法，每次转移，宣布'这
  ▎ 个替我们承担'的部分就更隐蔽了一层。我称之为责任洗钱。这本书是诊断工具。"

  如果一句话说不清楚，那后面的一切都没有锚点。作者在注记里说："I did not set out
  to write about it. I mentioned the noticing to people I trusted, and learned
  that most of them had noticed it
  too."——论点是先被反复口述、反复测试，才变成书的。

  第 2 步：用手工方法做完一个完整案例（2-3 天）

  不用任何 AI。 自己查资料、自己分析、自己写。

  对这本书来说，最早的案例可能是阿布格莱布（Abu
  Ghraib）——一个清晰的"追责停在低层士兵，不爬上指挥链"的案例。

  你要做的：
  - 找到原始文件（Taguba 报告、Fay-Jones 报告、参议院军事委员会调查）
  - 自己回答八问诊断
  - 自己判断这个案例属于四种分类中的哪一种
  - 自己写一份分析

  为什么不用 AI？ 因为你必须自己先搞清楚"做好是什么样的"，才能判断 agent
  有没有做对。如果你自己都不知道正确答案，agent 的输出你看不出问题。

  第 3 步：从案例中提炼出规则（1 天）

  做完第一个案例后，你会自然发现一些问题。比如：

  - "我写这句话的时候，我确定我知道来源吗？" → 证据分级规则
  - "这个动词会不会太强了？" → 过度断言规则
  - "我倾向于把责任全给 A，但 B 其实也有角色" → 分类规则

  把这些写成规则。不是 16 条，是 3-5 条。每条一句话。这些就是你最初的宪法。

  第 4 步：写出第一条"无法容忍的错误"（10 分钟）

  回顾你手工做的案例，问自己：如果我的书里出现这类错误，我会觉得这本书不值得出版
  。 把它写下来。

  对这本书来说，可能是："一句话里断言了一个人'knowingly'做了某事，但我没有证据证
  明他知道。"

  这就是你的第一条规则。也是你第一个 hook 的扫描目标。

  ---
  Phase 2：单 Agent 验证——检验你的规则

  第 5 步：把规则写成 Agent 的系统提示词（1 小时）

  把你的 3-5 条规则写成一个 agent 文件。不是 15 个。一个。

  ---
  name: researcher
  description: 分析案例，输出结构化分析报告
  tools: Read, Write, Grep, Glob, WebSearch, WebFetch
  model: opus
  ---
  # Role
  你分析责任洗钱案例。必须遵循以下规则：
  1. 每一条事实性断言必须标注证据等级（A/B/C/D）和来源
  2. 不允许使用 knew/deliberately/lied/proves/clearly 等动词
     除非引用了明确证明该状态的来源
  3. ...

  用 Claude Code 调这个 agent，让它分析你手工做过的同一个案例。

  第 6 步：人对比（最重要的一步）

  把 agent 的输出和你的手工输出并列对比。Agent 在哪里比你强？在哪里犯了你会避免
  的错误？在哪里看起来不错但仔细读发现过度断言了？

  这一步决定了你后续所有规则的质量。 你会发现 agent
  犯的错误类型，而这些错误类型就是你需要加更多规则的原因。

  第 7 步：迭代规则

  把 agent 犯的错加到系统提示词里。再跑。再对比。直到 agent
  的输出在关键维度上不差于你自己的输出。

  ---
  Phase 3：第一条 Pipeline——两个 Agent 串联

  第 8 步：加第二个 Agent（审查者）

  第一个 agent 做分析。第二个 agent 只做一件事：找问题。

  ---
  name: checker
  description: 审查研究者的输出，找过度断言、证据缺口、分类错误
  tools: Read, Write, Grep, Glob
  ---

  给 checker 一个明确的输出格式：

  Found issues:
    - [Location] [Severity: HARD/SOFT] [Description]
  Verdict: PASS / REVISE / BLOCK

  这就是 Laura 的雏形。 不是一开始就有 13 个 agent。是第二个 agent
  自然地要求存在——因为你自己对比 agent 输出和你的手工输出太累了，需要一个 agent
  帮你做。

  第 9 步：定义 Handoff schema（30 分钟）

  两个 agent 之间怎么交接？你发现如果 researcher
  不在输出末尾写明"我的假设是什么"和"我建议下一步做什么"，checker
  就不知道该以什么标准审查。

  于是你定义：

  Owner: ...
  Assumptions: ...
  Handoff: ...

  规则 5（Handoff cleanly）就是从这里来的。 不是因为"设计原则"，是因为你运行两个
  agent 时发现缺了这个字段就跑不通。

  第 10 步：跑通一整章（1-2 天）

  从案例 → 分析 → 核查 →
  初稿，跑通一整章的完整流程。不需要完美。但需要跑通。跑通意味着你找到了
  pipeline 的瓶颈和断点。

  这个项目自己管这叫"proof-of-shape"——第二章是 proof-of-shape。做完第二章证明了
  pipeline 可行，然后才并行推其他 12 章。

  ---
  Phase 4：规模化——从一章到全书

  第 11 步：从多章中发现全局规则

  做完第二章、开始做第三章时，你会发现有些规则是跨章的：

  - "第二章里讲过的一个概念，第三章用的时候变了味" → 术语管控 R51
  - "第三章引用的一个证据卡片，第二章也引用了但用了不同的措辞" → vocabulary
  registry
  - "第二章埋了一个伏笔，第三章需要回收" → callback 注册表

  全局规则不是事先设计的。是做到跨章时才发现需要的。

  第 12 步：写第一个 Hook

  当你在审查 agent 输出时，第 10 次手动搜索 knew 这个单词的时候——你就该写 hook
  了。

  # scan-overclaim.py 的第一个版本
  # 只扫描一个词：knew
  import sys, json
  data = json.load(sys.stdin)
  content = data.get("content", "")
  if "knew" in content.lower():

  Hook 来自痛苦。 每次你发现自己在手动做重复检查，就该写 hook。

  第 13 步：写第一个测试

  当 hook 逻辑变复杂，或者有多个 hook 同时运行时，你开始不确定"改了 A 会不会破坏
  B"。这时写第一个测试。

  先测试 hook 本身——给它一个包含 banned verb 的输入，断言它 flag 了。

  再测试 live repo——打开实际 agent 文件，断言 frontmatter 符合约束。

  核心教训

  这 16 步可以归结为三个原则：

  1. 先做具体工作，让架构从工作中长出来。
     不是先设计 15 个 agent 的蓝图，
     而是先做一章，发现你需要第二个 agent。

  2. 先用手工建立"好"的标准，再让 agent 去复制。
     自己不知道正确答案的事，
     交给 agent 你也看不出它错在哪里。

  3. Hook 和测试来自痛苦，不来自远见。
     每次手动重复检查同样的东西 → 写 hook。
     每次不确定改了会不会破坏东西 → 写测试。
